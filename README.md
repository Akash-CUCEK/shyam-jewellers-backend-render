# Shyam Jewellers Backend

Spring Boot modular monolith for Shyam Jewellers. The backend includes authentication, admin, users, products, categories, orders, invoice PDF generation, OTP login, Redis, JWT, email, Cloudinary, and a production-ready payment module.

## Payment Architecture

The payment module is implemented under `com.shyam.payment` and integrates with the existing `Order` entity without rewriting order APIs.

Core components:

- `Payment`: one payment attempt for an order.
- `PaymentTransaction`: immutable operational records for create, verify, retry, cancel, refund, and expiry actions.
- `PaymentGatewayResponse`: raw gateway response storage for audit and dispute investigation.
- `PaymentAudit`: internal status transition and security audit log.
- `PaymentGatewayProvider`: gateway abstraction for `MOCK`, `RAZORPAY`, `PHONEPE`, and `CASHFREE`.
- `PaymentEventPublisher`: no-op notification extension point for future Kafka or notification integration.

The default concrete provider is `MOCK`. Live providers can be added by implementing `PaymentGatewayProvider` and registering the provider as a Spring bean.

## Payment Flow

1. Create order.
2. Create payment for the order with an idempotency key.
3. Order moves to `PENDING_PAYMENT`.
4. Payment request is generated by the configured gateway provider.
5. Customer completes payment at the gateway.
6. Backend verifies gateway payment id, gateway order id, amount, and signature.
7. On success, payment moves to `SUCCESS`, order moves to `PAYMENT_SUCCESS`, order payment status moves to `PAID`, and invoice PDF generation is allowed.
8. On failure, payment moves to `FAILED`, order moves to `PAYMENT_FAILED`, and invoice generation remains blocked.

## Order Lifecycle

Supported order states:

`CREATED`, `PENDING_PAYMENT`, `PAYMENT_SUCCESS`, `PAYMENT_FAILED`, `CONFIRMED`, `PROCESSING`, `SHIPPED`, `DELIVERED`, `COMPLETED`, `CANCELLED`, `REFUNDED`, `PENDING`.

Existing order statuses remain valid for backward compatibility.

## Payment Lifecycle

Supported payment states:

`CREATED`, `PENDING`, `PROCESSING`, `SUCCESS`, `FAILED`, `CANCELLED`, `REFUND_INITIATED`, `REFUNDED`, `EXPIRED`.

`COMPLETED` is retained as a backward-compatible enum value but new payment flows use `SUCCESS`.

## Payment APIs

- `POST /api/v1/payments/create`
- `POST /api/v1/payments/verify`
- `POST /api/v1/payments/failure`
- `POST /api/v1/payments/{paymentId}/retry`
- `POST /api/v1/payments/{paymentId}/cancel`
- `POST /api/v1/payments/refund`
- `GET /api/v1/payments/{paymentId}`
- `GET /api/v1/payments/orders/{orderId}/history`
- `GET /api/v1/orders/{orderId}/payment`

Create, retry, and refund operations require an idempotency key through either `Idempotency-Key` header or request body.

## Configuration

Payment configuration is environment-driven:

```yaml
payment:
  currency: INR
  request-ttl-minutes: 20
  gateway:
    provider: MOCK
    signature-secret: ${PAYMENT_GATEWAY_SIGNATURE_SECRET}
    checkout-base-url: ${PAYMENT_GATEWAY_CHECKOUT_BASE_URL}
  urls:
    callback-url: ${PAYMENT_CALLBACK_URL}
    success-url: ${PAYMENT_SUCCESS_URL}
    failure-url: ${PAYMENT_FAILURE_URL}
```

Environment variables are listed in `.env.example`.
